\section{Weight and activation compression}
\label{sec:weights}

Weight compression is the first optimization on everyday devices because it attacks both terms that make a laptop unusable: the memory \emph{floor}~\eqref{eq:weights} and the bytes moved per decode step~\eqref{eq:roofline}.

\subsection{Affine quantization}

Affine quantization~\citep{jacob2018quantization} maps a real weight \(x\) to a \(b\)-bit integer code
\begin{equation}
  q = \mathrm{clip}\!\left(\mathrm{round}\!\left(\tfrac{x}{s}+z\right),\, 0,\, 2^{b}-1\right),
  \qquad
  \hat{x} = s\,(q-z),
\end{equation}
with scale \(s\) and zero-point \(z\), typically shared by a group of \(G\) weights (e.g.\ 64 or 128). Per-tensor scales are cheaper to store but fail when a matrix has a few huge outliers; per-channel or group-wise scales are the local default. Reconstruction error per element is on the order of half a quantization bin, \(|x-\hat{x}| \lesssim s/2\). Lower \(b\) forces a larger typical \(s\) for the same dynamic range, which is the quality--size tradeoff.

A numeric sketch: \(s=0.05\), \(z=8\), \(x=0.42\) yields \(q=\mathrm{round}(0.42/0.05+8)=16\) and \(\hat{x}=0.40\). Matmuls use many such \(\hat{x}\), not the original FP16 values. Two 4-bit codes pack into one byte,
\[
\mathrm{byte} = (q_0 \bmod 16) + 16\cdot (q_1 \bmod 16),
\]
so kernels unpack, dequant, and multiply in registers; Python never loops per weight. Scale metadata \(M_{\mathrm{scales}}\) is usually \(<1\%\) of weight bytes, so
\[
M_{\mathrm{weights}} \approx \frac{N\cdot b_w}{8}
\]
remains the planning equation. Table~\ref{tab:wmem} is the number a 16/24/64\,GB owner actually needs.

GPTQ was motivated by 175B-class models that could not fit on a single GPU~\citep{frantar2022gptq}; the same math now makes 8B models comfortable on a laptop---an inversion of the original constraint that is the everyday-device story.

\subsection{Post-training methods for LLMs}

Local stacks almost never run the calibrator at serve time. They \emph{load} a checkpoint produced by one of the following.

\textbf{GPTQ}~\citep{frantar2022gptq} quantizes weights column-by-column. After rounding a column, it uses a Hessian-aware update so remaining weights compensate for the rounding error (optimal brain compression in one shot). It needs a small calibration set and is the ancestor of many GGUF/GPTQ files.

\textbf{AWQ}~\citep{lin2023awq} does not treat all channels equally. It measures activation magnitudes, identifies \emph{salient} weight channels, and rescales or protects them so 4-bit rounding does not destroy the directions the network actually uses. In practice AWQ 4-bit is often the most robust ``download and go'' format for chat models.

\textbf{LLM.int8()}~\citep{dettmers2022llmint8} keeps a tiny set of outlier features in 16-bit during 8-bit matmul. It explains why naive INT8 of transformers collapses: a few channels dominate.

\textbf{SmoothQuant}~\citep{xiao2023smoothquant} migrates quantization difficulty from activations into weights via a per-channel smoothing factor \(s_j\), enabling W8A8. That path matters more when activations are quantized (prefill, large batch) than in single-stream FP16-activation decode on a laptop.

\textbf{OmniQuant}~\citep{shao2024omniquant} learns quantization parameters. Rotation / incoherence methods---QuaRot~\citep{ashkboos2024quarot}, SpinQuant~\citep{che2024spinquant}, QuIP\#~\citep{tseng2024quip}---apply orthogonal transforms so weights look more Gaussian and 4-bit (even 2-bit) bins are better used. Additive residual codebooks (AQLM~\citep{egiazarian2024aqlm}) and sparse-quantized hybrids (SpQR~\citep{frantar2023spqr}, SqueezeLLM~\citep{kim2023squeezellm}) store a tiny high-precision outlier set plus a compressed dense remainder. QServe~\citep{lin2024qserve} co-designs W4A8KV4 with a serving engine.

GGUF~\citep{gguf} exposes a zoo of layouts (Q4\_K\_M, Q5\_K\_M, Q8\_0, IQ2\_XXS, \ldots) that mix group sizes and super-blocks. ``4-bit'' in MLX, GPTQ, AWQ, and Q4\_K\_M are \emph{not} the same random variable (Section~\ref{sec:runtime}).

Bit width \(b_w \in \{16,8,4,2\}\) is a first-class serving knob. Empirically, \textbf{4-bit is the default sweet spot on unified-memory laptops}: 8-bit still spends too much DRAM for a daily driver; 2-bit frequently shows quality cliffs (Section~\ref{sec:empirical}). On a 24\,GB Mac, changing \(b_w:16\to 4\) is both a fit trick and a speed trick: Llama~3.1~8B decode goes from \(\approx 5.8\) to \(\approx 20.5\) tokens/s because each step reads \(\approx 4\times\) fewer weight bytes.

\subsection{Activation quantization, mixed precision, pruning, distillation}

Activation quantization (W8A8, W4A8) matters when GEMM is compute-bound or when activation RAM dominates---more common in prefill and large-batch serving than in single-stream decode, where weights dominate the traffic. Mixed precision (AMP) keeps accumulators in FP32 while storing weights in FP16/BF16; it is the default, not an extra flag, in most GPU stacks.

Pruning~\citep{han2015deep,frantar2023sparsegpt,ma2023llmpruner} removes weights. Unstructured sparsity needs specialized kernels to beat dense 4-bit GEMM on a laptop; if the kernel still reads a dense 4-bit block, you paid quality for no bandwidth win. Structured (channel/head) pruning is easier to serve but harder to keep accurate. Knowledge distillation~\citep{hinton2015distilling,sanh2019distilbert} produces a smaller student: it is a \emph{different model}, not a runtime switch, but it is often the highest-leverage ``optimization'' if a 1--3B student meets the product bar---the Phi/TinyLlama/OpenELM bet~\citep{abdin2024phi3,zhang2024tinyllama,mehta2024openelm}.

\section{KV cache and context memory}
\label{sec:kv}

\subsection{Why the cache exists}

Scaled dot-product attention~\citep{vaswani2017attention} is
\begin{equation}
  \mathrm{Attention}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_h}}\right)V.
\end{equation}
Recomputing \(K,V\) for the entire history at every decode step would repeat \(O(T)\) work per token. Caching per-layer \(K\) and \(V\) makes decode \(O(1)\) cache appends plus attention against the stored history. Equation~\eqref{eq:kv} then grows linearly in \(T\).

Worked Llama-class 8B numbers (\(L=32\), \(H_{\mathrm{kv}}=8\), \(D=128\)) make the ``KV does nothing'' myth go away:

\begin{center}
\small
\begin{tabular}{@{}lccc@{}}
  \toprule
  \(T\) & FP16 KV & 4-bit KV & When you feel it \\
  \midrule
  640 (default bench) & \(\approx 84\)\,MB & \(\approx 21\)\,MB & Hidden under 5\,GB weights \\
  4096 (short RAG) & \(\approx 536\)\,MB & \(\approx 134\)\,MB & Visible on 16\,GB \\
  32k (long context) & \(\approx 4.3\)\,GB & \(\approx 1.1\)\,GB & Rivals the 4-bit checkpoint \\
  \bottomrule
\end{tabular}
\end{center}

On a 24\,GB machine with 4-bit 8B weights ($\approx 5$\,GB), the cache is a rounding error at \(T=640\) and first-class at long RAG, multi-turn agents, or many concurrent sequences. Short-chat A/B tests that ``prove KV quant does nothing'' are measuring the wrong \(T\). Our M3 w4 vs.\ w4+KV deltas at default \(T\) are \(\approx -1.5\%\) tokens/s---insurance, not a short-chat speedup.

\subsection{Fewer KV heads}

Multi-query attention~\citep{shazeer2019mqa} shares one KV head across all query heads (\(H_{\mathrm{kv}}=1\)). Grouped-query attention~\citep{ainslie2023gqa} interpolates, with \(H_{\mathrm{kv}} \ll H_q\) (Llama~3 8B uses \(H_q=32\), \(H_{\mathrm{kv}}=8\), a \(4\times\) cache cut versus MHA). This is an \emph{architectural} reduction of \(M_{\mathrm{KV}}\) and of cache bandwidth. It explains why two 7B models can have very different long-context RAM slopes, and why Llama-3-class GQA is so friendly to laptops. Multi-head latent attention in DeepSeek-class models~\citep{liu2024deepseek} compresses KV further by storing a latent, then up-projecting---another architectural lever, not a serving flag.

\subsection{Quantizing the cache}

KV quantization stores cached \(K,V\) at \(b_{\mathrm{kv}} < 16\) (commonly 8, 4, or 2). It is independent of \(b_w\): FP16 weights + 4-bit KV is legal and useful when you refuse to quantize weights for an eval night but still want long \(T\). Group-wise affine quantization of cache rows is the same algebra as weights. KIVI~\citep{liu2024kivi} uses \emph{asymmetric} 2-bit KV (keys and values quantized differently) without fine-tuning. KVQuant~\citep{hooper2024kvquant} targets million-token contexts with per-channel and pre-RoPE tricks. Quality impact is usually smaller than aggressive weight quantization because each decode step only \emph{reads} the cache rather than using it as the model's entire knowledge. On-device, enable it as insurance once 4-bit weights have created headroom---especially on 16\,GB machines.

\subsection{Paging, prefix reuse, eviction, and sparsity}

\textbf{PagedAttention}~\citep{kwon2023vllm} stores KV in non-contiguous blocks of (typically) 16--64 tokens, analogous to virtual memory, so a serving engine can pack many sequences without reserving a giant contiguous buffer per request (Figure~\ref{fig:paged}). A laptop running one chat does not need a pager; a laptop running local \texttt{llama-server} for a household does. Without paging, fragmentation from variable-length chats wastes the same DRAM the OS needs.

\textbf{Prefix / prompt caching} reuses KV for a repeated system prompt or RAG template of length \(T_{\mathrm{sys}}\). Cold TTFT pays prefill of \(T_{\mathrm{sys}}+T_{\mathrm{user}}\); warm TTFT pays only \(T_{\mathrm{user}}\) (plus a cache lookup). For a 2k-token system prompt and a 128-token question, that is the difference between ``spinner'' and ``instant.'' It is the local analogue of a provider's prompt cache and one of the highest-ROI everyday-device tricks.

\textbf{Eviction} drops tokens believed unimportant: H\(_2\)O keeps heavy-hitter tokens with large attention mass~\citep{zhang2023h2o}; StreamingLLM keeps an \emph{attention sink} (first few tokens) plus a sliding window~\citep{xiao2024streamingllm}, which is why infinite-chat demos do not OOM; SnapKV~\citep{li2024snapkv} and Quest~\citep{tang2024quest} select what to keep given the query; DuoAttention~\citep{xiao2024duoattention} splits retrieval heads from streaming heads. Sliding-window attention (Mistral-style) bounds KV by construction~\citep{mistral2023}: \(T\) in~\eqref{eq:kv} is replaced by \(\min(T,W)\). These trade exact long-range attention for a bounded RAM envelope---exactly the phone/laptop deal.

\section{Attention kernels and prefill}
\label{sec:prefill}

Naive attention materializes \(S \in \mathbb{R}^{n \times n}\) per head. At \(n=2048\) and FP16 that is already \(\approx 8\)\,MB per head per layer; times \(L \times H\) this is gigabytes of intermediates---unacceptable on a laptop at long context. Compute is still \(\Theta(n^2 d_h H)\) for the \(QK^{\top}\) and softmax-\(V\) products.

FlashAttention~\citep{dao2022flashattention} tiles \(Q,K,V\) through on-chip SRAM, uses an online softmax~\citep{milakov2018online}, and never writes the full score matrix to HBM. For each block it tracks a running row-max \(m_i\) and row-sum \(\ell_i\):
\begin{align}
  m_i^{\mathrm{new}} &= \max(m_i^{\mathrm{old}}, m_{ij}), \\
  \ell_i^{\mathrm{new}} &= e^{m_i^{\mathrm{old}}-m_i^{\mathrm{new}}}\ell_i^{\mathrm{old}} + e^{m_{ij}-m_i^{\mathrm{new}}}\ell_{ij},
\end{align}
and rescales the output accumulator so the result matches standard attention up to floating-point order. FLOPs remain \(\Theta(n^2)\); extra memory is \(O(n)\). FlashAttention-2/3 improve work partitioning and low-precision paths~\citep{dao2023flashattention2,dao2024flashattention3}. On Apple Silicon, MLX implements tiled Metal attention internally; user code rarely toggles a ``Flash'' flag (Figure~\ref{fig:flash}).

\begin{figure}[t]
  \centering
  \includegraphics[width=0.92\linewidth]{figures/flashattention.png}
  \caption{IO-aware tiled attention (redraw after Dao et al.). Long RAG prompts on a laptop are exactly when avoiding the \(n\times n\) score matrix matters.}
  \label{fig:flash}
\end{figure}

The user-visible leftover knob is often \textbf{chunked prefill} with step size \(C\)~\citep{agrawal2023sarathipreprint,agrawal2024sarathi}. A prompt of length \(T_p\) is processed in \(\lceil T_p/C\rceil\) chunks. In our harness, ``prefill off'' is \(C=512\) and ``on'' is \(C=2048\). For \(T_p=512\) both are a single chunk (so the flag looks useless). For \(T_p=2048\), off means four chunks and on means one: less loop overhead and better kernel occupancy. Smaller \(C\) lowers peak activation memory and, in servers, lets decode tokens mix with partial prefills. Larger \(C\) often lowers TTFT when the device is under-occupied.

A simple TTFT model is
\begin{equation}
  \mathrm{TTFT} \approx \frac{\mathrm{FLOPs}_{\mathrm{prefill}}}{\mathrm{GPU\ throughput}} + \frac{M_{\mathrm{read}}}{B_{\mathrm{mem}}}.
\end{equation}
When attention dominates, doubling \(T_p\) can push TTFT up superlinearly. On M3 with Llama~3.1~8B w4 we measured \(\approx 2.4\)\,s at \(T_p=256\), \(\approx 5.8\)\,s at \(1024\), and \(\approx 15.4\)\,s at \(2048\) (Section~\ref{sec:empirical}).

Long-prompt prefill is where everyday RAG dies. MInference~\citep{jiang2024minference} sparsifies prefill attention dynamically. Sparse and local attention~\citep{child2019sparse,beltagy2020longformer} reduce the \(O(n^2)\) term by restricting the pattern. State-space models~\citep{gu2023mamba} change the architecture to linear time. Rotary embeddings~\citep{su2024rope} and YaRN~\citep{peng2023yarn} extend usable context without a full pretrain; they do not by themselves reduce \(M_{\mathrm{KV}}\).

On a MacBook, the first prefill optimization is still application-level: retrieve fewer chunks (Section~\ref{sec:app}). The second is prefix cache. The third is kernels and \(C\).

\section{Decode-time algorithms}
\label{sec:decode}

\subsection{Speculative decoding}

Baseline decode costs \(\approx T_g \cdot \tau_t\) where \(\tau_t\) is one target-model forward, so \(\mathrm{tok/s} \approx 1/\tau_t\). Speculative decoding~\citep{leviathan2023speculative,chen2023speculative} uses a cheap draft to propose \(k\) tokens; the target verifies them in one parallel forward and accepts a prefix of length \(m \le k\) under a rejection-sampling rule that preserves the target distribution (Figure~\ref{fig:spec}). The first rejected position is resampled from the target; remaining draft tokens are discarded.

Let \(\alpha\) be the per-token acceptance probability (in our harness, \texttt{draft\_accept\_rate}). Under an i.i.d.\ approximation the expected accepted length per round is \((1-\alpha^{k+1})/(1-\alpha)-1\) plus the bonus resampled token. Idealized wall-clock speedup when verification batches well is
\begin{equation}
  \mathrm{speedup} \approx \frac{k\cdot \tau_t}{\tau_d + \tau_{\mathrm{verify}}},
\end{equation}
and in practice we see \(1.4\)--\(2\times\) when \(\alpha \gtrsim 0.7\) and \(\tau_d \ll \tau_t\). If the draft is a poor match, one still pays \(\tau_d + \tau_{\mathrm{verify}}\) and can \emph{lose} throughput---we measure this on Llama~3.1~8B at \(\alpha=58.6\%\) (Section~\ref{sec:empirical}).

Memory is the everyday-device constraint:
\begin{equation}
  M_{\mathrm{peak}} \approx M_{\mathrm{target}} + M_{\mathrm{draft}} + M_{\mathrm{KV,t}} + M_{\mathrm{KV,d}}.
\end{equation}
A 0.5B 4-bit draft is \(\approx 0.25\)\,GB---cheap only after 4-bit \emph{target} weights have freed \(\sim 11\)\,GB relative to FP16. Draft and target must share tokenizer vocabulary. Our MLX path uses \texttt{num\_draft\_tokens}\( = k = 3\) and a family-matched small instruct model.

\textbf{Medusa}~\citep{cai2024medusa} attaches extra heads to the target instead of a second model---attractive on phones where loading two graphs hurts. \textbf{EAGLE}~\citep{li2024eagle} drafts at the feature level using a lightweight autoregressive head on hidden states. \textbf{SpecInfer}~\citep{miao2024specinfer} verifies token \emph{trees}. Lookahead and blockwise methods~\citep{chen2021lookahead,stern2018blockwise,spector2023rest} and Jacobi-style parallel decoding~\citep{santilli2023jacobidecoding} iterate several future positions. Deja Vu~\citep{liu2024dejavu} skips compute via contextual sparsity rather than drafting tokens.

On everyday devices speculation is a \emph{fourth} lever: it needs leftover RAM, a compatible draft, and a kill-switch when \(\alpha\) drops. CUDA graphs / Metal capture replay a static decode graph and cut launch overhead once shapes stabilize; they help small-batch latency and are complementary, not a substitute for bits.

\section{Batching, scheduling, and disaggregation}
\label{sec:serving}

Local \texttt{generate()} loops are single-stream. Production serving is not. We include this family because (i)~the same human may later run \texttt{llama-server} for a household, and (ii)~papers in this family invented paging and chunked prefill that local stacks now expose as flags.

\textbf{Static batching} waits to fill a batch of size \(B\), pads to the longest sequence, and holds every request until the slowest finishes. It under-utilizes bursty interactive traffic and inflates latency.

\textbf{Continuous batching} (iteration-level scheduling)~\citep{yu2022orca,kwon2023vllm} mixes prefill of new requests with decode of in-flight ones at every model forward. The unit of scheduling is a step, not a whole request. Combined with PagedAttention, this is why vLLM can keep a GPU full without reserving worst-case KV per session.

\textbf{Chunked prefill} in Sarathi-Serve~\citep{agrawal2024sarathi} piggybacks decode tokens alongside partial prefills so a 32k-token prompt cannot stall every interactive user. The same idea appears as \texttt{prefill\_step\_size} on a laptop, where the ``other users'' are just the rest of your decode stream.

\textbf{Disaggregated prefill/decode}~\citep{patel2024splitwise,aminabadi2024distserve} places the two phases on different pools because prefill is compute-heavy and decode is KV-/bandwidth-heavy; the objective is goodput, not raw tokens/s. A household analogue would be ``prefill on the desk Mac, decode on the laptop,'' which almost nobody runs yet (Section~\ref{sec:open}).

SGLang~\citep{zheng2024sglang} adds a radix cache (prefix tree over KV) and compiled structured generation. Request scheduling adds SLOs, preemption, and priority (chat versus batch jobs). These policies do not change Equations~\eqref{eq:peak}--\eqref{eq:roofline}; they change \emph{who} holds the KV pages and \emph{when} a prefill is admitted.

On a daily-driver laptop with one user, continuous batching does almost nothing. On a Mac mini serving a family, it suddenly does. The mistake is cargo-culting vLLM flags before the model fits beside Safari.

\section{Parallelism}
\label{sec:parallel}

When one device cannot hold the model, inference reuses training sharding.

\textbf{Tensor parallelism}~\citep{shoeybi2019megatron,narayanan2021efficient} splits GEMMs inside a layer (column-parallel \(W_{\mathrm{up}}\), row-parallel \(W_{\mathrm{down}}\)) and all-reduces activations. Latency can drop if interconnect is fast (NVLink); it \emph{rises} if all-reduce dominates a small decode step---the usual case at batch 1 on consumer PCIe.

\textbf{Pipeline parallelism}~\citep{huang2019gpipe} assigns consecutive layers to devices. Bubble time is painful at batch 1 unless micro-batches exist; a single interactive user is the worst case.

\textbf{Expert parallelism} for MoE~\citep{fedus2022switch,lepikhin2021gshard,jiang2024mixtral} routes tokens to expert shards. Memory is proportional to \emph{total} experts; compute per token is proportional to \emph{active} experts. Mixtral 8\(\times\)7B is a 47B-class memory object with \(\approx 13\)B active parameters: attractive on 64\,GB, painful on 24\,GB. EdgeMoE~\citep{yi2023edgemoe} specifically targets on-device MoE by prefetching experts.

\textbf{Data parallelism} replicates weights and splits the batch; natural for large-batch throughput, useless for one chat.

Consumer Macs almost never expose multi-GPU tensor parallel for LLMs; the relevant decision is ``does this dense 70B fit in unified memory at 4-bit?'' (usually no on 24\,GB; \(\approx 35\)\,GB of weights plus KV on 128\,GB Ultra is plausible). A single consumer NVIDIA GPU plus CPU/SSD offload~\citep{sheng2023flexgen,song2024powerinfer,alizadeh2024llm} is the PC analogue: PowerInfer keeps hot neurons on GPU and cold ones on CPU; LLM-in-a-flash pages weights from NAND. These are \emph{fit} strategies that sacrifice tokens/s. They are how a gamer GPU runs a 70B at all, not how a 24\,GB Mac should serve an 8B.

\section{Architecture and model-size choices}
\label{sec:arch}

The highest-leverage ``optimization'' on a small machine is sometimes a smaller model. Memory~\eqref{eq:weights} and bandwidth-bound decode~\eqref{eq:roofline} both scale with \(N\). A dense 0.5B 4-bit model and a dense 8B 4-bit model can differ by an order of magnitude in tokens/s on the same laptop (Section~\ref{sec:empirical}): Qwen~2.5~0.5B at 238 tokens/s versus Llama~3.1~8B at 21 tokens/s versus Gemma~2~9B at 15 tokens/s, all at 4-bit on M3.

Phi-3~\citep{abdin2024phi3}, TinyLlama~\citep{zhang2024tinyllama}, OpenELM~\citep{mehta2024openelm}, MobileLLM~\citep{liu2024mobilellm}, Gemma~2 2B~\citep{team2024gemma2}, and Llama~3.2 1B/3B exist because of that curve: they are not ``toy models,'' they are the models that fit beside iOS and Android. Mixture-of-experts~\citep{jiang2024mixtral,liu2024deepseek} offers more total parameters at a smaller active-FLOP budget, at the cost of a larger memory floor. Long-context variants (32k--128k) do not change \(N\) but inflate \(T\) in~\eqref{eq:kv} and prefill cost; buying a 128k checkpoint without KV quant or sliding windows is how 24\,GB machines swap. Instruction-tuned versus base checkpoints should be held fixed in systems benchmarks; they are not speed knobs.

A practical ladder for everyday devices: 0.5B--1B for always-on / phone; 3B for a capable pocket model~\citep{gunter2024apple,abdin2024phi3}; 7--9B 4-bit for a 24\,GB laptop assistant; 27--32B 4-bit for 64\,GB desks; 70B only with quantization, offload, or a workstation.

\section{Adapters}
\label{sec:lora}

LoRA~\citep{hu2022lora} injects low-rank updates \(\Delta W = BA\) with \(B\in\mathbb{R}^{d\times r}\), \(A\in\mathbb{R}^{r\times k}\), \(r\ll \min(d,k)\). Parameter count per adapted matrix is \(r(d+k)\) instead of \(dk\). QLoRA~\citep{dettmers2023qlora} fine-tunes those adapters on a quantized base---the reason a laptop can specialize an 8B model overnight without a second 16\,GB copy of the weights. At inference, each adapter adds a small extra GEMM (\(xA\) then \((\cdot)B\)) and a small RAM footprint (often tens of megabytes per adapter at \(r=16\)). Multi-LoRA serving keeps many adapters resident and batches across different \(B,A\) pairs; that is a server problem (vLLM, SGLang). For a single local user, one LoRA is usually noise compared with \(b_w\), and it is how ``my coding style'' becomes an on-device file rather than a cloud fine-tune.

\section{Compilation, kernels, and runtimes}
\label{sec:runtime}

Graph compilation (\texttt{torch.compile}, \texttt{mlx.compile}, XLA, TensorRT-LLM~\citep{nvidia2024trtllm}, MLC~\citep{mlcllm}) fuses ops, specializes shapes, and can capture a decode step as a single graph. Quantized matmul kernels determine whether 4-bit is actually faster than FP16 or merely smaller: naive dequant-then-FP16-GEMM can lose the roofline win by doubling traffic. Fused dequant-GEMM (Marlin-class CUDA kernels, MLX Metal INT4, llama.cpp \texttt{q4\_K} SIMD/Metal) is the difference between ``4-bit is slower'' folklore and the \(3.5\times\) we measure.

CPU/disk offload~\citep{sheng2023flexgen,alizadeh2024llm} runs models that do not fit, at a large bandwidth penalty (PCIe or NAND vs.\ DRAM). Memory-mapping weights from SSD reduces cold-start RAM spikes: the OS loads pages on first touch. That helps \emph{launch}, not steady-state decode, unless you accept thrash.

\section{Application-level inference}
\label{sec:app}

Not every latency problem belongs inside the model---especially on everyday devices, where the user controls the prompt.

Retrieval-augmented generation~\citep{lewis2020rag} can \emph{increase} TTFT by stuffing thousands of tokens into \(T_p\). If a retriever returns \(k\) chunks of \(c\) tokens, prefill cost scales with \(kc\) (and attention with \((kc)^2\)). Cutting \(k\) in half is often a larger TTFT win than a new kernel. Rerank-then-truncate, smaller chunk size, and ``answer from memory unless retrieval is needed'' are inference optimizations. Prefix caches absorb repeated templates. Semantic prompt caches reuse prior completions for identical questions (agents that retry tools).

Constrained / structured decoding~\citep{willard2023outlines,zheng2024sglang} masks logits toward JSON or grammars; it adds CPU work per token and can reduce sample diversity, but it prevents the ``retry the whole 8B forward because the JSON was invalid'' loop---often a net win on a laptop. Early-exit and confidence stopping~\citep{schuster2022confident} cut \(T_g\) when the model is already sure. Nucleus and temperature~\citep{holtzman2020nucleus} are quality knobs with mild speed effects via average \(T_g\). Tool/function calling~\citep{alizadeh2024llmcompiler} is an application graph; on a laptop, serial tool loops (search \(\rightarrow\) read \(\rightarrow\) generate) dominate wall-clock more than GEMM.

The daily-driver heuristic: \textbf{every token you do not retrieve is a token you do not prefill.}
